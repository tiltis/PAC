# PAC2026 센서별 인수조건과 검증 범위

작성: 2026-10-04. 기준: `04_실행계획/PAC2026_구현_단계별계획_20261002.md`, 사용자가 명확히 한 동일 물체 데이터 연결 요구.

## 핵심 요구와 이번 구현

3대 카메라의 엄밀한 픽셀 정합은 전체 완료 조건이 아니다. 한 시료를 세 센서의 공통 시야에 고정하고, 검사면·회차별 촬영이 끝날 때까지 이동·교체하지 않는 조건에서 데이터를 연결한다. 요청 ID가 같다는 사실만으로 물리적으로 같은 물체임을 증명하지 않는다. 자동 시각 재식별은 구현하지 않았고 정확도를 보장하지 않는다.

각 `/inspect` 요청은 `session`, `specimen_id`, `face`, `attempt`, 새 `trigger_id`를 갖는다. 응답과 저장 메타데이터를 대조하며, 각 면·재촬영·반복 검사에는 서로 다른 트리거를 사용한다. RGB/열화상 취득 시각은 요청 이후부터 촬영 종료 사이에 있어야 한다. 뎁스는 요청 이후 새 프레임만 받으며, SDK 장치 시각의 반복·역행도 거부한다.

시간 차의 허용값은 현장에서 측정한 `sensor/calib/timing_policy.json`으로 명시한다. 정책이 없으면 시각 차는 기록하되 `linked_by_request_only`로 표시한다. 유효한 시간 정책과 호출자의 고정 단일 시료 전제가 있으면 `linked_under_stationary_specimen_precondition`으로 표시한다. 이 상태도 자동 물체 재식별 성공을 뜻하지 않는다. 깊이 입력이 누락·오래됨·무효이면 그 상태를 기록하고, 필수 입력 모드에서는 측정 불가와 포장당 1회 재촬영 규칙을 적용한다.

## 센서별 인수조건

| 센서/경로 | 최초 목적 | 구현한 인수조건 | 남은 실장비 확인 |
|---|---|---|---|
| RGB | 면 A/B 영상과 닫힘 검사 자료 | uint8 BGR PNG, 시료·면·회차·트리거·수신 시각 연결, 요청 이전 영상 거부, 어두움·흐림 품질 검사 | 해당 노트북에서 실제 프레임, 단일 시료 고정, USB 대역폭·노출 상태 확인. 닫힘 결함 규칙은 라벨 자료 확보 후 검증 |
| 열화상 | 단열/냉매 관련 보조 특징 | Y16 uint16 `stack[n,256,320]` 원본 보존, raw_counts 단위, 정지·포화 품질 검사, 취득 창과 RGB 시각 차 기록, 상대 색상 미리보기 분리 | 실제 Y16 반복 취득·FFC·예열·기준 패치 재현성, 보유 장비와 노트북에서의 동시 취득 확인 |
| 뎁스 | 선택 기능: 거리·자세 확인, 뚜껑 높이 차 보조 기록 | 명시적 `-Depth` 옵션에서만 SDK 취득, uint16 원시값 × SDK scale = mm, 0 무효값 제외, 유효 픽셀 비율·거리 중앙값·시각·원시 파일 기록. 실측 면별 ROI/거리 허용범위가 있을 때만 자세 범위 판정 | 실제 장치의 사용 가능한 Y16 프로파일·scale·증가하는 장치 시각 확인. 물체 ROI·면별 거리 허용범위 실측. 뚜껑 높이 결함 규칙은 이번에 만들지 않음 |
| 센서 연결 | 동일 물체의 같은 검사 회차 기록 | 요청·응답·메타·원시 파일·DB의 ID와 트리거 연결, 다른 시료/트리거/회차 거부, 과거 프레임 거부, 재촬영·반복 검사 트리거 분리 | 촬영 중 한 물체만 고정하는 운영 조건 확인, 허용 가능한 RGB/열/깊이 시각 차 측정. 시야 밖 물체·중간 교체의 시각적 자동 검출은 미구현 |
| 스테이션 기록 | 두 면 결과와 추적 가능성 | `sensor_data`, `artifacts`, `trigger_id`를 DB에 보존. 기존 DB에 열만 추가하며 기록 보존. `GET /api/runs/{run_id}/inspections`로 상세 조회 | 현장 PC 간 HTTP·파일 조회와 실제 저장 위치 확인 |

## 단위와 기능 제한

- 열화상은 현재 비방사측정 Y16 원시값으로 처리한다. 대상의 섭씨 온도 변환이나 단열 결함 임계값을 만들지 않았다. `target_temperature_c=null`이며 `fpa_sensor_temperature_c`는 검출기 내부 온도다. 대상 온도가 아니다.
- 열화상 `raw_min/max/mean`은 원시 카운트다. 색상 PNG는 상대 미리보기이며 분석 원본은 `lwir_y16.npz`다.
- 뎁스는 `DepthFrame.get_depth_scale()`의 mm/raw-count 값을 사용한다. 깊이 좌표계이며 Arducam RGB와 정렬됐다고 표시하지 않는다. ROI가 없으면 전체 깊이 프레임의 중앙값이다. 이를 물체 거리로 자동 해석하지 않는다.
- 뎁스 유효성의 기본 2초 제한은 기존 스트림 상태 확인과 같은 운영상 최신성 검사다. 결함 임계값이나 동일 물체 보장값이 아니다. 동일 촬영의 시각 차 허용값은 별도 현장 정책으로 설정한다.
- RGB-열화상 ROI 대응 기능만 `H_faceA/B.json`, `roi_faceA/B.json`을 필요로 한다. 파일이 없으면 해당 ROI 특징만 계산하지 않는다. 동일 시료 데이터 기록, 뎁스 원시 거리 기록과 전체 촬영 파이프라인은 사용할 수 있다.
- 열화상 정량 결함 판정은 라벨된 정상/닫힘 틈/단열재 누락/접촉 대조군 자료와 독립 평가 세션이 없으므로 `review`를 유지한다. 유효한 깊이 거리·시각 연결도 결함 검사 통과를 의미하지 않는다.

## 실행과 최소 입력

이번 작업은 실카메라나 로봇을 작동시키지 않았다. 다음은 사용자가 장비를 준비한 뒤 실행하는 절차다. 실행 중인 센서 서버가 있다면 별도 서버를 중복 실행하지 않는다.

1. RGB·Boson·Gemini 2를 장착하고 한 시료가 세 시야에 들어오는지 확인한다. 물체/센서를 촬영 중 이동하거나 교체하지 않는다. 검사면과 시료 ID를 기록한다.
2. SDK 의존성은 선택 파일 `sensor/requirements-depth.txt`에 명시했다. 현재 개발 환경의 `pyorbbecsdk2==2.1.2` 스텁을 근거로 구현했으며 새 설치·드라이버/관리자 설정·펌웨어 변경은 수행하지 않았다.
3. 사용자가 센서 서버를 시작할 때 `run_sensor.bat -Depth`로 깊이를 보조 기록하거나, `run_sensor.bat -Depth -RequireDepth`로 누락/무효 깊이를 측정 불가 처리한다. 기본 실행은 깊이를 열지 않는다. `-Fake`와 실제 `-Depth`의 혼용은 거부한다. Orbbec 장치가 정확히 한 대이고 Gemini 2인지 확인한 뒤에만 깊이 스트림을 시작하며, 장치 이름·일련번호·펌웨어를 촬영 메타에 남긴다. 여러 장치가 있으면 다른 프로젝트 장치를 임의 선택하지 않는다.
4. 적어도 같은 시료의 A/B면, 첫 촬영/재촬영, 같은 시료 반복 검사를 수집한다. `meta.json`, `vis.png`, `lwir_y16.npz`, `depth_raw.npz`, `inspect.json`이 있으면 장비 조작 없이 원본 재생·ID·단위·시간 검증이 가능하다. 깊이 누락 시 원시 파일이 없음을 명시한다.
5. 시간 연결을 검증하려면 `timing_policy.json.example`을 참고해 실제 취득 세션으로 허용 시각 차를 정하고 `timing_policy.json`으로 저장한다. 예제는 null과 `validated=false`를 포함하므로 실행 정책으로 자동 적용하지 않는다.
6. 깊이 자세 게이트가 필요할 때만 `depth_policy_faceA.json.example`을 참고해 깊이 픽셀 ROI, 면별 거리 하한/상한, 최소 유효 비율을 실측해 A/B 정책을 만든다. 임의 수치를 기본값으로 제공하지 않았다.

## 검증 방법과 실제 확인 범위

`python -m pytest sensor/tests station/tests -q -p no:cacheprovider`로 단위·실패·반복·통합 검증을 수행한다. 테스트는 SDK 모의 프레임, FakeRig, MockRobot, HTTP TestClient/MockTransport와 별도 DB를 사용한다. 모의 시험 통과는 실장비 연결이나 과학적 모델 정확도를 입증하지 않는다.

인수 테스트는 스케일/시계 구분, 0 무효값, 오래된 프레임, 반복 장치 시각, 다른 시료/트리거, 시각 차 정책, 필수 뎁스 누락 후 재촬영, 회차별 고유 트리거, 원시 파일 및 상세 메타의 HTTP/DB 전달, 기존 DB 이전 기록 보존, 저장 실패 롤백·재실행을 포함한다.

기존 실측 기록은 2026-10-03 Gemini 2 1280×800 스트리밍 로그와 2026-10-02 Boson 안정성 CSV 9행이다. CSV의 프레임 평균은 21695.63~21787.0 raw counts이고 FPA 내부 온도는 44.2~44.3°C다. 해당 CSV에는 물체의 섭씨 온도나 깊이 거리 배열이 없다. 기본 데이터 위치에서 현재 재생할 실제 Y16/깊이 원본 배열을 확인하지 못했으므로 새 원본 샘플이 필요하다.

읽기 전용 포트 조회에서는 8000/8001 리스너가 없고 Laya의 8766 리스너만 확인됐다. 따라서 기본 주소의 PAC 서비스는 현재 응답하지 않는다. 프로세스 상세 조회가 접근 제한으로 실패해 시작 안 됨/종료/다른 포트의 구체 원인은 미확인이다. 어떤 프로세스도 종료·재설정하지 않았다.

## SDK 근거

- 로컬 설치된 `pyorbbecsdk2 2.1.2`의 `DepthFrame`, `Frame`, `Pipeline`, `StreamProfileList` 스텁: 깊이 스케일, 장치 시각(ms), 스트림/프레임 API.
- [Orbbec 공식 깊이 예제](https://github.com/orbbec/pyorbbecsdk/blob/v2-main/examples/beginner/02_depth_visualization.py): uint16 × depth scale = mm. 예제의 표시용 거리 제한값은 PAC 결함 임계값으로 가져오지 않았다.
- [Orbbec 공식 예제 목록](https://github.com/orbbec/pyorbbecsdk/blob/v2-main/examples/README.md): 자체 depth-color 정렬과 보정/포인트클라우드 기능. 이것을 별도 Arducam RGB/열화상과의 정렬 증거로 해석하지 않는다.


## Claude 읽기 전용 리뷰 반영 (2026-10-04)
- 분류 결정(final_verdict/bin)은 후속 실패에도 보존한다. decision_status는 결정 여부,
  routing_status는 실행 상태, placed_bin은 목표함 도착 후 그리퍼 열기 명령 성공을 뜻한다.
  placed_bin도 실제 시편 낙하/존재 센서 확인은 아니다. 이전 DB는 새 상태가 NULL이며 추정하지 않는다.
- 촬영 후 정책/디코딩 오류에서도 capture_id, artifacts, 요청 trigger_id를 보존하고 inspect.json에 오류를 남긴다.
- 통신 시간 초과의 기록에도 생성된 trigger_id와 session을 유지한다.
- Station HTTP 클라이언트는 single_stationary_specimen=false로 보낸다. 명령/그리퍼/안정화 성공만으로
  단일 시편 존재를 확인하지 못하므로, 실제 근거가 구현되기 전에는 정지 시편 전제를 주장하지 않는다.
- 실장비 성공 응답에는 pac-sensors-1과 일치하는 association이 필요하다. 기존 명시적 모의 응답은
  MockRobot 테스트에서만 정상 분류에 쓰며 실장비의 정상 판정을 허용하지 않는다.
- 깊이 비활성화 시 잔존 depth policy는 로드/적용하지 않는다.
- 깊이 장치 시계 역행 시 기존 프레임을 버린다. 이전 기준보다 낮은 장치 timestamp가 3개 연속 증가하면
  새 clock epoch 기준을 설정하되 이 3개는 사용하지 않는다. 이후 증가 프레임만 받는다.
  반복 timestamp는 복구로 인정하지 않으며 요청은 설정된 timeout deadline 안에 종료한다.
  이는 소프트웨어 복구 규칙이며 실제 장치 리셋 동작은 미검증이다.


## 부분 저장 실패와 검사별 오류 보존
촬영 폴더 생성 직후 capture_request.json에 시편/면/시도/trigger_id를 기록하고,
PNG/NPZ/전체 메타 저장 실패 예외에도 해당 폴더 경로를 보존한다. 최소 요청 기록 자체가
실패하면 디스크 기록을 보장할 수 없지만, 응답의 capture_id/trigger_id와 inspect.json 저장 시도로 추적한다.
검사별 error 및 persistence_error는 inspections 테이블의 추가 열에 저장하며 기존 행은 NULL로 유지한다.
운영 DB를 재구축하거나 삭제하지 않는다.
single_stationary_specimen=false는 안전한 미확인 상태다. 단일 시편 존재와 촬영 중 정지의
실물 검증은 대기 중이며, 그 근거가 구현·검증되기 전에는 true로 바꾸지 않는다.

## 2026-10-06 실장비 확인 추가

- **Gemini 2 장치 시각 고정**: 펌웨어 1.4.92, Windows에서 `get_timestamp()`가 모든 프레임에서 같은 값(292057776)이었다. 깊이만 켠 상태에서도 같았다. 기존 "장치 시각 반복·역행 거부" 규칙 때문에 첫 프레임 뒤로 모든 프레임이 버려졌다(실측 약 0fps). 이제 SDK 프레임 번호(`get_index()`, 1씩 증가)로 순서를 판단하고, 장치 시각은 기록만 한다. 기록에는 `frame_index`와 `order_key`가 들어간다. 수정 후 RGB 30fps, 열화상 60fps, 깊이 약 31fps를 동시에 받았다.
- **깊이 시작 오류 2건 수정**: ① SDK `Context`를 변수에 담지 않아 "NULL pointer ... deviceMgr" 오류가 나던 문제, ② 깊이를 먼저 열면 Windows COM 초기화 방식이 엇갈려 카메라 이름 조회가 실패하던 문제.
- **시편 ID 마커**: RGB에서 ArUco 번호를 읽어 요청한 시편 번호와 비교하고(`marker.py`) 결과를 기록만 한다. 시각적 자동 재식별은 아니며 정확도를 보장하지 않는다. 마커가 없거나 가려지면 `marker_match=null`이다.
- **실시간 3화면**: 센서 `/live.jpg`(실장비 응답 약 0.1초), 스테이션 `/sensor-live`, 웹 화면의 "실시간 카메라" 카드. 화면용이며 촬영 기록에는 쓰지 않는다. 깊이 색 범위 200~1500mm는 보기용이고 측정 범위가 아니다.
- **3카메라 같은 물체 확인(objects.py)**: 빈 장면 배경과의 차이로 RGB·열화상·깊이에서 각각 가장 큰 물체 덩어리를 찾는다. 물체를 4곳 이상 놓아 모은 중심 대응점으로 RGB→열화상, RGB→깊이 호모그래피를 맞춘다. RGB 물체 위치를 옮긴 예상 위치와 각 카메라에서 찾은 물체 중심이 화면 폭의 8% 안이면 일치로 본다. 결과(`object_status`, 카메라별 bbox·넓이, 열화상 Δcount, 깊이 거리)는 기록·화면용이며 판정에 쓰지 않는다. 실온 물체는 열화상에서 안 보일 수 있다. 가상 장면 시험만 통과했고, 실물 상자 확인은 아직이다.
